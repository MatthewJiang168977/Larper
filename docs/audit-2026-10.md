# Audit, October 2026

Reviewed on 2026-10-17 at commit `b843f4e` (after milestone 8 and the ranking-query and
chain-size follow-ups): the README, the web app (`apps/web`), the API (`apps/api/src`),
the Go workers (`workers/`), the migrations (`db/migrations`), the Helm chart
(`infra/helm/larper`) and the load-test results. Nothing was run for this audit; every
item comes from reading the code and docs, and line numbers refer to that commit.

**How it's ordered.** Impact on the core loop (get a quest, walk there, check in) and on
users' data first, then the safety nets that catch regressions and outages, then ranking
quality and polish. Within a tier, cheaper items come first. Effort: **S** is under a day,
**M** a few days, **L** a week or more.

---

## 1. Check-in uses a coarse, possibly stale position

**Problem.** "I went" sends whatever position `useLocation` last stored
(`apps/web/components/quest/quest-home.tsx:73`). That position comes from
`watchPosition` with `enableHighAccuracy: false` (`apps/web/hooks/use-location.ts:67`),
and a new fix is dropped unless it is at least 40 m from the stored one (`MIN_MOVE_M`,
lines 19 and 52-54). A more accurate fix that arrives within 40 m never replaces a
coarse one, and its `accuracyM` is lost with it. The API allows 75 m plus the
reported accuracy capped at 50 m (`apps/api/src/quests/quests.service.ts:28-29,
155-170`). So someone standing at the door can get "You're 110 m away", and moving a few
steps won't fix it because those fixes are filtered out.

**Why it matters.** Check-in is the end of the core loop and the strongest taste signal
(+0.20). A false 422 at the door is the worst moment to fail. Nothing in the load tests
covers it, since k6 posts exact coordinates.

**Fix.** On "I went", ask for one fresh fix (`getCurrentPosition` with
`enableHighAccuracy: true, maximumAge: 0`, short timeout) and send that. Keep the
40 m filter for refetching the deck, but always keep a fix whose accuracy is better than
the stored one. Show "Getting a precise fix…" while waiting. **Effort: S.**

## 2. Error and loading states are misleading or get stuck

**Problem.**
- The error banner (`quest-home.tsx:131-134`) shows raw API text (`500 Internal Server
  Error`, Nest's `Internal server error`), has no dismiss or retry, and is only cleared by
  a later successful `/quests/today` (line 42). After a failed action (lines 76-77) nothing
  refetches, so a 422 from a check-in stays on screen until the user moves 40 m.
- If `/me` fails (line 29), `me` stays null, `/quests/today` never runs, and the bottom
  label reads "Surveying the area…" (lines 137-139) under the error forever. The same
  label is also the generic loading text, so it means two things: loading, and a real
  ingest in progress (lines 121-128).
- Onboarding's "Try again" after a failed save calls `restart()`
  (`apps/web/app/onboarding/page.tsx:67, 75-82`), which throws away every swipe; it should
  retry the POST with the same answers.
- No error boundary or `error.tsx` exists in `apps/web/app`, so a render error blanks the
  page.

**Why it matters.** These are the states users see when anything goes wrong (item 4 makes
a Postgres blip a 500). They currently read as "the app is surveying" or as jargon.

**Fix.** A small error component that maps status to copy ("Can't reach the server.
Retrying…" for 5xx/503 using `Retry-After`, the API's own message for 4xx), a retry
button, and auto-clear on the next action. Separate "Loading your quest…" from "Surveying
the area…". Retry the onboarding POST without resetting state. Add `app/error.tsx`.
**Effort: S.**

## 3. Every service connects as the same database user

**Problem.** The API (`infra/helm/larper/templates/api.yaml:44-45`), outbox-relay and
taste-worker (via `larper.workerEnv`, `templates/_helpers.tpl:9-10`), ingest-worker
(`templates/workers.yaml:112-113`) and the migrate Job (`templates/migrate.yaml:27-28`)
all read `DATABASE_URL` from the CNPG `pg-app` Secret. That user, `larper`, owns the
database and every table (`templates/postgres.yaml:40-42`), so each pod can run any DDL,
read every user's taste and location history, or `DROP TABLE`. The README already hit a
practical cost: the API's "no parallel workers" setting had to go into the pool's
connection options because `ALTER ROLE` would have changed it for the workers too
(README "Ranking-query fix", and `apps/api/src/db/db.module.ts:14-17`).

**What each service actually uses** (from the SQL in the code; tests and load-test SQL
excluded):

| Role | Tables and privileges |
|---|---|
| `larper` (owner, migrate Job only) | DDL; owns everything, including golang-migrate's `schema_migrations` |
| `larper_api` | `users` SELECT, INSERT (`auth/users.service.ts`); `taste_profiles` SELECT, INSERT, UPDATE (`profile/profile.controller.ts`, `quests.service.ts`); `quests` SELECT, INSERT, UPDATE (`quests.service.ts`); `outbox` INSERT (`events/outbox.ts`); `jobs` SELECT, INSERT (`jobs/job-queue.ts`, `quests/areas.service.ts`); SELECT on `places`, `area_stats`, `area_totals`, `areas_ingested`, `tags` |
| `larper_relay` | `outbox` SELECT, UPDATE, DELETE (`cmd/outbox-relay/main.go`: claim with `FOR UPDATE`, mark sent, prune after 7 days) |
| `larper_taste` | `processed_events` INSERT; `taste_profiles` SELECT, INSERT, UPDATE (`SELECT … FOR UPDATE` needs UPDATE); `places` SELECT (`cmd/taste-worker/main.go:146-193`) |
| `larper_ingest` | `places` SELECT, INSERT, UPDATE; `tags` INSERT, UPDATE (`syncTags` runs on every load); `areas_ingested` INSERT, UPDATE; `area_stats`, `area_totals` SELECT, INSERT, DELETE (`internal/places/places.go`, `internal/stats/stats.go`); `jobs` SELECT, UPDATE (`internal/queue/queue.go`, `sqs.go`); TEMPORARY on the database (`CREATE TEMP TABLE stage`), which PUBLIC has by default |

No service needs DELETE on `users`, `quests` or `taste_profiles` today, and only the API
needs to read `users`. `load-places` (run by hand through a port-forward) can use the
ingest role. Identity columns should need no separate sequence grant, but the role test
below should confirm it.

**How CNPG can provide it.** Declare the roles in the Cluster under
`spec.managed.roles` (`login: true`, `connectionLimit`, `passwordSecret`). CNPG does not
generate passwords for managed roles: each needs a `kubernetes.io/basic-auth` Secret
(`username`, `password`), created by the deploy scripts or by the chart (`lookup` so an
upgrade doesn't rotate it). CNPG also does not manage table grants, so those live in a
migration. The app gets a URI by building it from the Secret's fields plus the `pg-rw`
host in the Deployment env, since only `pg-app` carries a ready-made `uri`. Per-role
settings then become possible: `ALTER ROLE larper_api SET max_parallel_workers_per_gather
= 0` can replace the connection option.

**Rollout under expand/contract.** Migrations run as a pre-upgrade hook
(`templates/migrate.yaml:14`) and must work for pods still running. The order:

1. **Release N (expand: roles).** Add the managed roles and their Secrets. No migration,
   no pod changes. CNPG creates the roles while every pod still uses `pg-app`. A migration
   in this release could not grant to them: the pre-upgrade hook runs before Helm updates
   the Cluster, so the roles wouldn't exist yet, and `larper` lacks `CREATEROLE`.
2. **Release N+1 (expand: grants, then switch).** Migration 0010 grants the table above
   (and `ALTER DEFAULT PRIVILEGES` only if we accept broad grants on future tables; the
   stricter choice is explicit grants in every migration that adds a table). Its down
   migration revokes them. It runs before pods roll, so the new pods, now pointing at
   their own Secrets, find their grants in place, and old pods keep working as `larper`.
3. **Contract.** Nothing to drop: `larper` stays the owner and the migrate Job keeps
   `pg-app`. Optionally stop mounting `pg-app` anywhere but the Job.

Risks: a missing grant is a runtime `permission denied` on one code path, so add a test
that connects as each role and checks `has_table_privilege` against the table above (and
that, say, the API role cannot `DELETE FROM users`). Every new table from now on needs
grants in its own migration. Restores (`postgres.restore.enabled`) bring the roles back
from the backup; CNPG then resets their passwords from the Secrets, so the Secrets must
survive a rebuild (`infra/oci-k3s/README.md` should say so). The README's local
`load-places` command reads `pg-app` and would need the ingest Secret.
**Effort: M.**

## 4. A Postgres outage returns 500, and readiness ignores dependencies

**Problem.** When Postgres is down, `pg` connect timeouts (5 s,
`apps/api/src/db/db.module.ts:13`) surface as unhandled errors, so Nest answers 500; there
is no exception filter (`apps/api/src/main.ts`). The README records 143 such 500s during
the chaos test and says a 503 with `Retry-After` would be more accurate. `readyz` still
returns ready unconditionally, with a `TODO(milestone 2)` (`health/health.controller.ts:13-17`).
`offer()` also throws a bare `Error('offer vanished')` (`quests.service.ts:336`), another
500.

**Why it matters.** 500 says "bug"; 503 with `Retry-After` says "try again", which the web
app (item 2) and k6 can act on. Error-rate panels can't tell outages from bugs.

**Fix.** A global filter that maps connection errors (`ECONNREFUSED`, pool connect
timeout, SQLSTATE class 08, `57P01`-`57P03`) to 503 with `Retry-After: 5`. Leave
`readyz` independent of Postgres on purpose (if every pod went unready during an outage,
Traefik would have no endpoints and answer 503s without the header), and say so in the
code instead of the stale TODO. Re-run `loadtest/chaos.sh` to confirm 503s.
**Effort: S.**

## 5. No CI: tests and schema checks only run by hand

**Problem.** The only workflow is `.github/workflows/oci-probe.yml`. The Jest suite
(`pnpm api:test`), Go tests (`workers/...`), `buf lint` / `buf breaking`, `helm
template` / lint, and the web app's typecheck and ESLint never run on a push or PR. The
DB-backed tests (`candidates.db.spec.ts`, `internal/stats`, `internal/queue`) skip
unless `TEST_DATABASE_URL` is set. The web app has no tests at all.

**Why it matters.** Several past fixes are protected only by tests (the MMR equivalence,
the additive-scoring regression, the chain lock race). They help only if something runs
them. `buf breaking` matters more as M9 adds a second consumer of `user.events`.

**Fix.** One `pull_request` workflow with no secrets: pnpm install, API Jest, web
`tsc` + lint, `go test ./...` and `go vet`, `buf lint` + `buf breaking --against main`,
`helm lint` / `helm template` for each values file. A second job with a
`postgis/postgis` service container runs the migrations up and down and then the
DB-backed Go tests. `candidates.db.spec.ts` needs NYC data, so it stays manual.
**Effort: S** for the first job, **M** with the database job.

## 6. No account deletion, and precise location history is kept indefinitely

**Problem.** Users are created lazily (`auth/users.service.ts`), and the Clerk webhook is
deferred (README "Lazy user creation"). Deleting an account in Clerk leaves the `users`
row, the taste vector and the quest log. Every quest stores `origin`, the user's exact
position when it was offered (`db/migrations/0003_quests.up.sql`), with no retention
limit, and outbox payloads hold user and place ids for 7 days
(`cmd/outbox-relay/main.go:25`). Separately, the Clerk dev instance stops at 100 users,
which already shapes the load tests (60 test users in use; README "Load test").

**Why it matters.** A per-user location history is the most sensitive data in the system,
and M9's profile work will add more per-user data and a public share route. There is
currently no way to honour a deletion.

**Fix.** The cascades already exist (`ON DELETE CASCADE` from `users`), so deletion is one
`DELETE FROM users`. Add either a Clerk `user.deleted` webhook (needs a signing secret
in the API, which the README currently avoids holding) or a signed-in
`DELETE /me`. Coarsen or drop `origin` after the offer resolves: the 5 km staleness check
(`quests.service.ts:303-311`) only needs it while the quest is `offered`. Plan the Clerk
production instance (or a test-only `SessionVerifier`, `auth/session-verifier.ts`, behind
a flag that never ships) before load tests need more than 100 users. **Effort: M.**

## 7. Workers are unobserved, and three tables grow without bound

**Problem.** Only the API has metrics: `templates/monitoring.yaml` has one
ServiceMonitor (`app: api`) and the only dashboard is `dashboards/api.json`. Consumer lag,
the outbox backlog, dead-lettered events and dead `jobs` are visible only through
`kubectl logs` and `rpk`. Meanwhile `processed_events` is never pruned (only inserted,
`cmd/taste-worker/main.go:146`), `jobs` keeps every `done` and `dead` row
(`internal/queue/*.go` has no DELETE), and `quests` grows with every expired offer (the
relocate cache-miss run expired 18,879 in one run).

**Why it matters.** The relay and taste-worker can stall with nothing on the dashboard
(the API keeps answering, it just stops learning). The tables only cost disk now, but
`processed_events` grows by one row per event per consumer, and M9 adds a consumer.

**Fix.** A small `/metrics` endpoint in `internal/platform` (Prometheus Go client) for
events applied/duplicate/dead-lettered, outbox unsent count and oldest age, jobs by
status; consumer lag from Redpanda's own metrics endpoint or computed in the worker; one
worker dashboard. Prune `processed_events` only past the longest time an event can stay
in the topic (an id older than that can't be redelivered). That isn't the 7-day
`retention.ms`: retention deletes whole closed segments and `segment.ms` is 14 days, so an
event can be redelivered for up to ~21 days (checked on the stack: Redpanda v24.2.7, both
values inherited defaults). Either prune at, say, 30 days, or set `retention.ms` and
`segment.ms` explicitly on the topic and prune at their sum. Prune `done` jobs past a week,
in the relay's existing cleanup
loop (`cmd/outbox-relay/main.go:64-69`) or in each owner. **Effort: M.**

## 8. Re-ingest can leave stale chain sizes and never removes places

**Problem.** `stats.Recompute` recounts only the chains present in the refreshed areas
(`workers/internal/stats/stats.go:37-46, 62-66`). `chain_key` is derived from name and
brand (`internal/taxonomy/taxonomy.go:178`), so a re-ingest that renames a place moves it
to a new chain key, and the old chain's other locations elsewhere keep a
`chain_locations` one too high. Separately, `upsert` only inserts and updates
(`internal/places/places.go:166-176`): a place that closes or loses all its tags in a
newer Overture release stays in `places` and can still be offered.

**Why it matters.** Today areas are ingested once (an area in `areas_ingested` is never
re-queued, `quests/areas.service.ts:30-38`), so both only bite on a bulk reload or an
Overture release bump. They will bite as soon as refreshing data is automated, and a
closed place as a quest is a bad experience.

**Fix.** Before the upsert, collect the old `chain_key`s of the rows being updated (and
of rows about to be removed) and pass them to `Recompute` with the new ones, under the
same advisory lock order. Add a test next to `TestRecomputeChainLocations` that moves a
place between chains. For removals, delete places in the refreshed area whose
`overture_id` isn't in the stage table (quests cascade, so consider a `retired_at` flag
instead to keep journal entries). **Effort: S** for chains, **M** with removals.

## 9. The 3,000-candidate cap cuts through ties by id

**Problem.** `candidates()` keeps the top `MAX_CANDIDATES = 3000` by taste, ties broken
by `p.id` (`apps/api/src/quests/quests.service.ts:22, 250-277`). In dense cells
thousands of places have zero taste and tie at the cap (one pair: 3,632 tied, 2,861
kept, README "Ranking-query fix"). Rarity and independence can still lift one of those
into the deck, so which ones survive matters. Ids follow load order, so the cut favours
places loaded first rather than anything meaningful. The cap also sets the API's cost on
a miss: parsing 3,000 rows is why a miss costs the API about 2.5x a hit.

**Why it matters.** Users with narrow profiles in Manhattan see a deck biased toward
whatever loaded first. The fix is also the README's listed next step for API CPU.

**Fix.** Order ties by something meaningful that is cheap in SQL: rarest-tag rarity is
too expensive there, but `confidence DESC` then `chain_locations ASC` (both on the row)
approximate the score's own multipliers. Then use the existing equivalence harness
(`loadtest/rank-bench.sh`, `candidates.db.spec.ts`) to find the smallest cap that leaves
the top 200 and the deck unchanged on the 200 pairs. **Effort: M.**

## 10. Accessibility and copy

**Problem.**
- `--ink-faint` (#8c8473) on `--paper` (#f2ead8) is about 3.1:1
  (`apps/web/app/globals.css:6, 11`), under WCAG AA's 4.5:1 for small text. It's used
  for the "No opening hours yet. Check before you go." warning (`quest-sheet.tsx:156`,
  `text-xs`) and the Skipped/Expired journal stamps (`app/journal/page.tsx:11-13`).
- "Abandon" on an accepted quest sends `skip` (`quest-sheet.tsx:190-191`), which applies
  the −0.05 taste penalty. A user who abandons because the place was closed (the app warns
  it has no hours) is told nothing and gets fewer places like it.
- Onboarding has no undo: a mis-swipe is permanent until the whole pass is redone
  (`app/onboarding/page.tsx:38-47`). The swipe card isn't focusable; arrow keys work only
  through a window listener with no on-screen hint.
- Lead tabs truncate names at 11rem with no title (`quest-sheet.tsx:101`).

**Fix.** Darken `--ink-faint` to at least 4.5:1 or keep it for decorative text only.
Make "Abandon" ask why ("Closed / Not for me"), and send a closed place as an action that
doesn't move taste (the event already distinguishes actions, so this needs a new
`QuestAction` value and a `buf breaking`-safe proto addition). Add an "Undo" button to
onboarding and a hint for the arrow keys. **Effort: S** (the "closed" action is M).
